# ts-gn-log v0.1 の実装を PR に分割する - Plan

> この文書は GitHub Issue に貼る本文の案。確定したら Issue 化し、以降は Issue 側を正本にする。
> 設計の根拠は [docs/designs/0001-ts-gn-log-design.md](../designs/0001-ts-gn-log-design.md)。

## この Issue の目的

設計案 0001 が定めた ts-gn-log v0.1 を、レビューできる大きさの PR に分割して並べる。各 PR に「何を入れるか」「完了と見なす条件」「依存する PR」を書き、着手順を決められる状態にする。

## 前提 (設計案 0001 の決定事項)

- リポジトリは public。配布は git 参照 + `dist/` をコミット
- TypeScript 7 系、ESM のみ、ランタイム依存ゼロ
- 分類 (`event` / `error_type` / `operation`) と `fingerprint` は既定では出さない
- ブラウザ側は対象外
- 出力の契約の正本は py-gn-log の main (#15 文脈、#17 Cloud Trace、#18 分類と fingerprint はマージ済み。設計案 §8)。片方だけで決めない

## PR の分割方針

- **1 PR = 1 つの動機**。「機能の追加」と「リファクタリング」と「ツールの自動生成物の更新」を混ぜない
- **`dist/` は PR 1 から常にコミットし、ソースを変えた PR ごとに再生成して更新する** (二重管理を防ぐ CI 検査があるため、分けると検査が通らない)。ただしコミットは分ける
- **README も PR 1 で骨組みを置き、機能を足す PR がその機能の節を書く**。機能とその文書は同じ動機なので同じコミットに入れる
- **契約に関わる PR (#3, #6, #7) は py-gn-log の main の実装・README・tests に合わせる**。py-gn-log 側に未決の点 (#26 など) があれば、ts-gn-log の実装で決めずに py-gn-log 側の Issue で合意を取る
- 各 PR は単独で `npm run build` / `npm test` / `npm run lint` が通る状態にする

## コミットの見積もりの前提

各 PR の「コミットの内訳」は、コミットルール (変更した動機ごとに 1 コミット。機能の追加/変更、修正、linter 指摘への対応、リファクタリング、ツールによる自動生成を混ぜない) に従った場合の見積もり。

- 機能のコード + そのテスト + 関連する文書の更新は同じ動機なので 1 コミット
- `dist/` の再生成はツールによる自動生成なので、それを生んだ変更とは別のコミット。`dist/` に影響する変更が 1 つの PR に複数あっても、再生成は PR の最後に 1 回まとめる
- linter の指摘対応はソースを書いた後に発生するもので、指摘の項目ごとに 1 コミット。件数は事前に読めないので「+α」として幅で示す
- 以下に挙げるのは「最低限これだけの動機がある」という数。作業中に判明した修正は別コミットとして増える

## リリース (版の付け方)

- **PR 3 (ロガー本体) のマージで `v0.1.0`** を付ける。それまで (PR 1, 2) は `version: 0.0.0` のまま、タグも打たない
- **PR 4 以降は、マージした PR ごとに版を上げてタグを打つ** (`v0.2.0`, `v0.3.0`, ...)。レビュー次第でマージの順番が入れ替わったり、マージできない PR が出たりするので、版番号を事前に PR に割り当てない。マージが決まった時点で、その PR の最後のコミットとして `version` を上げる
- 手順: `version` を上げるコミットを PR に足す → マージ → main にタグを打って push
- 利用プロジェクト A は必要な機能が入った版のタグを `"ts-gn-log": "github:tengine/ts-gn-log#v0.x.0"` で参照する

`version` を上げるコミットは各 PR の内訳に「マージ直前」として含めてある。

## 依存関係

```
PR 1 (足場 + README 骨組み + dist)
 ├─ PR 2 (CI) ──────────────────────┐
 ├─ PR 3 (ロガー) ─ PR 4 (文脈) ─ PR 5 (trace) ─┤
 └─ PR 6 (fingerprint) ──────────────┤
        PR 3, PR 6 ─ PR 7 (errorEvent) ─┘

版: PR 3 のマージで v0.1.0。PR 4 以降はマージごとに v0.2.0, v0.3.0, ... (順番はマージ時に決まる)
```

並行できるもの: PR 2 と PR 3、PR 3 系列と PR 6。

`dist/` を PR 1 から常にコミットするので、並行する PR は `dist/` で衝突する。衝突したら後からマージする側が main を取り込んで `dist/` を再生成する (手で解決しない)。
